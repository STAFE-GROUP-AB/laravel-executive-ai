# Data model — the Sprint 1 minimum (S1-01) and the §3.1 CRM (S2-01), AI (S2-02) and governance (S2-03) tables

**Status:** Living document · **Owner:** Workstream B (Laravel platform) · **Issues:** #29, #84, #85, #86
**Source of truth:** `database/migrations/` (the migrations are `up()`-only; the schema is built once
per CI job with `migrate`, tests run inside `DatabaseTransactions`, ADR-002 D10)

This page describes the tables §16 step 4 asks for — `users`, `organizations`, `memberships`,
`briefs`, `brief_items`, `brief_deliveries`, `audit_events` and the install-state marker — plus the
framework tables the `local` profile needs (`jobs`, `job_batches`, `failed_jobs`, `cache`,
`cache_locks`, `sessions`, `password_reset_tokens`), since S2-01 the §3.1 CRM and source tables,
since S2-02 the §3.1 AI, approvals, tool-run and memory tables, and since S2-03 the governance,
retention and operations tables (all in §2 below). Everything lives in one SQLite file in WAL mode
(ADR-002 D2). The remaining §3.1 tables — the mail store (`email_messages`, `email_threads` and the
rest of the `email_*` family, E3-2) — are added by their own backlog items on the same conventions.

## 1. Conventions (ADR-002 D10, blueprint §3.1)

| Rule | How |
|---|---|
| Identity | ULID as `char(26)`, generated by `HasUlids`. Primary key named `<table>_pk` — a name neither engine keeps: SQLite calls that index `sqlite_autoindex_<table>_1`, MySQL calls it `primary`. |
| Portable types | `string` + PHP enum instead of `enum` columns; `json()` for structured data; `boolean()`; all timestamps UTC `dateTime`. `char(26)` compiles to `varchar` on SQLite, whose grammar has no CHAR type. No raw SQL except the one generated column below and the full-text grammars (§2, "Full-text indexes"). |
| Named indexes | Every index and foreign key carries an explicit name (`<table>_<columns>_<unique|index|fk>`), so the MySQL profile and `schema:dump` diffs are stable. SQLite does not store foreign-key constraint names; the contract test asserts them where the engine keeps them and asserts the columns everywhere. |
| Common columns | Added by `App\Support\Database\BusinessObjectColumns` on every business table (next section). |
| Soft delete | `deleted_at` on objects a user can delete or a retention rule can expire gradually; **not** on append-only logs (`brief_deliveries`, `audit_events`). |
| Timestamps | `created_at`, `updated_at` as nullable UTC `dateTime`. |

### Foreign keys with no index of their own — read this before dropping an index on MySQL

**Measured on a clean MySQL 8.4 database while S2-04 (#87) was being built, and invisible to every
SQLite-only check.** InnoDB requires an index whose *leftmost* column is the referencing column of a
foreign key, and it will adopt an index that already satisfies that rather than create one. Laravel
adds foreign keys *after* the table's indexes, so wherever a `<table>_<columns>_unique` index starts
with the referencing column, that unique index is the only thing serving the foreign key — and
dropping it, or re-columning it, is refused outright:

```
SQLSTATE[HY000]: General error: 1553 Cannot drop index
'contact_emails_organization_address_unique': needed in a foreign key constraint
```

SQLite enforces no index for a foreign key at all, so the same migration succeeds there and the
failure only appears in the `server-profile` CI lane. **Nine foreign keys are currently in that
shape** — one serving index, and it is unique:

| Table | Foreign key | The only index serving it |
|---|---|---|
| `action_approvals` | `action_approvals_proposal_fk` | `action_approvals_proposal_unique (action_proposal_id)` |
| `contact_emails` | `contact_emails_organization_fk` | `contact_emails_organization_address_unique (organization_id, address_hash)` |
| `customer_contact` | `customer_contact_customer_fk` | `customer_contact_customer_contact_unique (customer_id, contact_id)` |
| `email_sync_cursors` | `email_sync_cursors_connection_fk` | `email_sync_cursors_connection_scope_unique (connection_id, scope)` |
| `mcp_grants` | `mcp_grants_tool_fk` | `mcp_grants_tool_active_unique (tool_id, active_marker)` |
| `memory_sources` | `memory_sources_memory_fk` | `memory_sources_memory_position_unique (memory_id, position)` |
| `project_contact` | `project_contact_project_fk` | `project_contact_project_contact_unique (project_id, contact_id)` |
| `sync_cursors` | `sync_cursors_external_account_fk` | `sync_cursors_account_scope_unique (external_account_id, source_type, scope)` |
| `task_assignees` | `task_assignees_task_fk` | `task_assignees_task_user_unique (task_id, user_id)` |

`brief_items_brief_fk` is the near miss worth knowing about: it is served by **two** unique indexes
(`brief_items_brief_item_unique`, `brief_items_brief_position_unique`), so dropping either one is fine
because the other takes over. Everything else in the schema has a non-unique index that can serve its
foreign key, either a composite one that happens to start with the right column or the index MySQL
created for the constraint itself.

**Nothing is wrong with any of these**, and none of them was changed: the index each one needs is the
index the queries want anyway. It is a hazard, not a defect — the next migration that touches one of
those unique indexes hits the same wall, on MySQL only, after every local check passed. The fix is
additive and is in
`2026_10_13_000013_encrypt_sensitive_attributes_at_rest::moveTheAddressUniqueIndexOntoTheHash()`: put
a **scaffold** index over the new column set up *first*, so the foreign key never has no index; then
drop the old one; then create the real index under its frozen name; then remove the scaffold, which is
safe because by then the named index is serving the constraint. Two indexes over the same columns
coexist for three statements, which both engines allow, and the final state is identical on each. The
query that produced the table above is in that migration's doc block; re-run it after any migration
that adds a unique index starting with a foreign-key column.

## 2. Tables

### `users`

Owner and user accounts. **Password-less by design**: login is a one-time code by email (S1-02), so
`password` is nullable and never seeded. `id` is a ULID; organization scope comes through
`memberships`. Soft-deletable.

| Column | Notes |
|---|---|
| `id` | ULID |
| `name`, `email` | `users_email_unique`; the address is stored lower-cased |
| `email_verified_at`, `password` (nullable), `remember_token` | stock Laravel columns kept for the guard; `email_verified_at` is set by the first verified one-time code |
| `last_login_at`, `login_count` | S1-02 login bookkeeping, written by `OtpVerifier` on every verified code |

`sessions.user_id` is `char(26)` to match, and the `sessions` table is the source of truth for
server-side revocation (`App\Security\Authorization\SessionRevoker`, [auth.md](auth.md) §5).
`password_reset_tokens` is kept for the framework and unused by the OTP flow.

### `passkey_credentials`

Registered passkeys (S2-05, [auth.md](auth.md) §7). A credential record like `otp_codes`, not a
business object: no organization, provenance or soft delete, and a removed passkey is deleted while
the removal stays in `audit_events`.

| Column | Notes |
|---|---|
| `user_id` | FK → `users.id` (`passkey_credentials_user_fk`) |
| `name` | the owner's label for the device ("Phone"), or a dated default |
| `credential_id` | base64url of the WebAuthn credential id, up to **1364** characters (the spec's 1023 bytes, base64url-encoded). Deliberately **not** indexed |
| `credential_id_hash` | `char(64)`, SHA-256 of `credential_id`; carries **`passkey_credentials_credential_id_hash_unique`** |
| `public_key` | base64 of the COSE public key — public by design, hidden from serialisation |
| `user_handle` | the user's ULID, as handed to the authenticator |
| `sign_count` | the authenticator's counter; a value that does not advance is refused |
| `aaguid`, `transports`, `attestation_type`, `trust_path` | what the ceremony reported (`attestation: none`) |
| `backup_eligible`, `backed_up`, `uv_initialized` | WebAuthn backup/UV state, kept consistent per the spec |
| `rp_id`, `origin` | the ADR-006 D3 origin this credential belongs to; every query is scoped by `rp_id` |
| `last_used_at`, `created_at`, `updated_at` | |
| indexes | `passkey_credentials_credential_id_hash_unique`, `passkey_credentials_user_rp_index (user_id, rp_id)` |

**Why the identity of a credential is indexed through a hash (#117).** The table originally put the
unique index on `credential_id` itself. On the `server` profile that is 1024 characters of `utf8mb4`
— **4096 bytes against InnoDB's 3072-byte key limit** — so `migrate` aborted on that file and, since
migrations run in order, every table after it was never created: the `server` profile was
unmigratable from a clean database. Shortening the column was not available, because a credential id
is up to 1023 bytes per the WebAuthn Level 2 spec and its base64url form reaches 1364 characters, so
`1024` was already short for a conforming authenticator.

So `credential_id` is wide and unindexed, and `credential_id_hash` carries the constraint.
`App\Models\PasskeyCredential::hashFor()` is the single definition, a `saving` hook recomputes the
column from `credential_id` on every write so no row can hold an index key that disagrees with its
credential id, and `forCredentialId()` is the only way the authenticator looks one up. The fix is
two migrations: the `create` migration was amended so a **fresh** database gets the right shape
(safe because `migrate` never re-runs an applied migration), and
`2026_10_13_000001_index_passkey_credential_id_by_hash` brings an **existing** database forward —
adding the column, backfilling it, moving the index — with every step guarded so it is a no-op on a
fresh one. `credential_id` is widened only off SQLite, which neither enforces nor even emits a
`VARCHAR` length, so the `local` profile needs no table rebuild and no existing row is rewritten.

The lane that would have caught it is now `server-profile` in `.github/workflows/ci.yml`: it
migrates a clean MySQL 8.4 database, asserts no migration is left pending, and runs the
`backend-contract` group — the ADR-002 D10 matrix that §5 below says must hold on both profiles.

### `brief_deliveries` — the idempotency key

Append-only attempt log (brief schema §2 "Idempotent delivery"). No soft delete, rows are never
updated.

| Column | Notes |
|---|---|
| `brief_id` | FK → `briefs.id` |
| `idempotency_key` | copied from the brief version at insert |
| `position` | index in `deliveries[]`; `brief_deliveries_brief_position_unique` |
| `channel` | `menubar` · `pwa` · `email` |
| `recipient` | approved address, or `menubar:local` / `pwa:local` |
| `attempt` | ≥ 1 |
| `status` | `queued` · `sent` · `failed` · `skipped` |
| `message_id`, `sent_at`, `error` (500) | |
| `sent_marker` | **generated column** `case when status = 'sent' then 1 else null end` |

Two unique indexes make a double send impossible to *record*, not just detectable:

1. **`brief_deliveries_idempotency_attempt_unique (idempotency_key, channel, recipient, attempt)`** —
   a retry that replays attempt *n* cannot insert a second row.
2. **`brief_deliveries_single_sent_unique (idempotency_key, channel, recipient, sent_marker)`** — the
   generated column is `1` for `sent` rows and `NULL` otherwise, and both SQLite and MySQL treat
   `NULL` as distinct in unique indexes, so any number of `queued`/`failed`/`skipped` rows may
   coexist with **exactly one `sent`** per target. This is the portable form of the partial unique
   index `… WHERE status = 'sent'` the schema document asks for (MySQL has no partial indexes).

The delivery job (S1-03) therefore: looks for an existing `sent` row for `(idempotency_key, channel,
recipient)`, records `skipped` if found, otherwise derives the mail `Message-ID` deterministically
from the key, channel and recipient, sends, and inserts the `sent` row — the index rejects a race.

### The §3.1 CRM and source tables (S2-01, #84)

Blueprint §3.2 makes the local CRM the system of record for customers, contacts, communications,
projects and todos; ADR-002 **D9** (final with this item) says how that relates to the provider's
own tables. Three rules run through all of it:

1. **`email_messages`/`email_threads` (E3-2) are the provider system of record**, and they *are*
   §3.1's `messages` and `threads` — no separate tables exist or will. `communications` is the
   source-agnostic CRM projection over them.
2. **A domain is not a customer.** `customers.email_domains` is a JSON hint with no unique index,
   because the fixture pack has two customers on `example.it` (§5.6) and matching by domain alone is
   a weak reason the matcher has to say so about.
3. Every table carries the §1.1 common columns through `BusinessObjectColumns`, including the pivots
   — a link between a customer and a contact has provenance and a soft delete like anything else.

Models live in `app/Models/CRM/`, all on the `CrmModel` base (common columns, casts, tenant
relation); the enums are in `app/CRM/<Module>/`. `App\CRM\Import\CrmPackMapper` reads and writes the
`packaging/fixtures/crm/*.json` shape — the JSON half of §3.2's import/export and the round-trip
oracle (§3 below).

### The §3.1 AI, approvals, tool-run and memory tables (S2-02, #85)

Nine tables: `ai_providers`, `ai_models`, `ai_runs`, `tool_runs`, `action_proposals`,
`action_approvals`, `memories`, `memory_sources`, `browser_sessions`. Models live in
`app/Models/AI/` and `app/Models/Approvals/`; the vocabularies are PHP enums in `app/AI/Compliance/`,
`app/AI/Runs/`, `app/AI/Tools/`, `app/AI/Memory/` and `app/Approvals/`. `ai_runs`, `tool_runs`,
`action_proposals`, `action_approvals` and `browser_sessions` are append-only and therefore carry no
`deleted_at`, like `brief_deliveries` and `audit_events`.

Four rules run through all of it:

1. **No credential, anywhere.** `ai_providers` stores `secret_service` / `secret_account` /
   `secret_version` — the coordinates of a Keychain generic-password item — and nothing else
   credential-shaped (ADR-003 D1). There is deliberately **no `headers` column**, which is where a
   bearer token for the `openai-compatible` driver would otherwise land. The contract test scans the
   table's column names against a forbidden-name pattern, so the next migration cannot add one.
2. **No binary column and no image path** on `tool_runs`, `audit_events` or `action_proposals`
   (ADR-003 D7 row 8, ADR-005 D1.7). A redacted frame lives in `Caches/` for the session's lifetime;
   the database keeps a SHA-256, the dimensions, the app bundle id and the window title.
   `tests/Security/AuditNoBlobTest.php` asserts the *shape of the schema*, not a clean row.
3. **The guarantee is an index, not a check** — ADR-009 D1.2's argument, reused four times: the
   dedupe slot on `ai_runs`, the idempotency key and nonce on `action_proposals`, the proposal and
   nonce on `action_approvals`, and the single active memory per key. Each uses either a plain unique
   index or the `brief_deliveries_single_sent_unique` generated-column idiom.
4. **Prompts, transcripts, tool arguments and results pass `App\Security\Secrets\Redactor` on
   write** (ADR-003 D7 row 4). They are text and JSON columns; nothing in them is a blob.

#### `ai_runs` — ADR-004 D7's thirteen provenance fields and the dedupe key

`App\AI\Runs\RunProvenanceField` maps each of D7's thirteen fields to its columns and the contract
test walks it:

| D7 field | Column(s) |
|---|---|
| `trace_id` | `trace_id` — a ULID per run, propagated to `tool_runs` and MCP calls, **never** sent as a header to an external provider |
| provider | `provider` (copied string) + `ai_provider_id` (FK) |
| model id | `model_id` (copied string) + `ai_model_id` (FK) |
| model digest | `model_digest` |
| quantization | `quantization` |
| privacy mode | `privacy_mode` (`App\AI\Routing\PrivacyMode`) |
| region evidence id | `region_evidence_id` → `ai_providers.id` (`ai_runs_region_evidence_fk`) |
| prompt hash | `prompt_hash` (`sha256:`, 71) |
| capabilities snapshot | `capabilities_snapshot` (json) |
| usage | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_write_input_tokens`, `reasoning_tokens`, `total_tokens` |
| cost | `cost_eur` `decimal(12,6)` |
| wall time | `wall_time_ms` |
| outcome | `outcome` |

`provider` and `model_id` are copied as strings next to their foreign keys on purpose: a run must
stay readable after the owner deletes the provider row. The rest of the control plane is recorded as
it was actually applied (`max_steps`, `steps_used`, `max_time_seconds`, `max_output_tokens`,
`max_cost_eur`), plus `started_at`, `finished_at`, `cancelled_at`, `cancellation_source`,
`finish_reason`, `error_kind`, `error_message`, and `prompt_redacted` / `response_redacted` (text,
`Redactor` on write — the stored response is what a dedupe hit returns).

`outcome` is `App\AI\Runs\RunOutcome`: `running` · `succeeded` · `failed` · `refused` · `cancelled`.
`cancelled` is required by ADR-004 D2 row 6 and is a first-class outcome, not a flavour of failure;
`refused` is the fail-closed path (missing capability, exhausted budget, open circuit, policy denial)
where nothing ran and nothing was degraded.

**The dedupe key** is D7's `sha256(job_class, normalized_input, model_id)`, built by
`AiRun::dedupeKey()`: the three parts are length-prefixed before hashing so no boundary can be
shifted, and the normalized input is canonicalised with RFC 8785 (`App\Support\Json\Jcs`, the brief's
rule) so two logically identical requests with differently ordered keys produce one key. Two columns
carry the window:

1. `dedupe_window_start` — the UTC start of the `dedupe_window_minutes` bucket (default 60,
   `AiRun::dedupeWindowStart()`). Without it the key would be unique forever and the same job could
   never run twice; with it a request repeated after the window inserts normally.
2. `dedupe_marker` — a **generated column**, `case when outcome in ('running', 'succeeded') then 1
   else null end`.

**`ai_runs_dedupe_window_unique (organization_id, dedupe_key, dedupe_window_start, dedupe_marker)`**
therefore admits any number of `failed` / `refused` / `cancelled` rows alongside **at most one** live
run per key and window — a replay inside the window is unrecordable, while a retry after a failure is
not blocked. Same idiom as `brief_deliveries_single_sent_unique`, same reason (MySQL has no partial
indexes). Other indexes: `ai_runs_trace_id_index`, `ai_runs_organization_started_at_index`,
`ai_runs_organization_provider_started_at_index` (what the €5.00-per-day cap sums over),
`ai_runs_organization_job_started_at_index`, `ai_runs_organization_outcome_index`.

#### `action_proposals` — frozen and immutable

§11's "frozen immutable proposal, input/recipient/hash, approver identity, expiry, nonce,
idempotency, fail closed", with ADR-005 D1.6's columns. The model only ever writes rows here;
nothing in the table carries authority on its own.

| Column | Notes |
|---|---|
| `kind` | `ui_action` · `outgoing_email` · `crm_deletion` · `github_write` · `external_form` — §11's approval-driven list (`App\Approvals\ProposalKind`) |
| `status` | `pending` · `approved` · `rejected` · `expired` · `executed` · `superseded` |
| `ai_run_id`, `trace_id`, `browser_session_id`, `proposed_by`, `requested_by_user_id` | where it came from; `proposed_by` uses the provenance actor grammar |
| `app_bundle_id`, `window_title`, `element_role`, `element_label`, `action_type` | ADR-005 D1.6's frozen target |
| `redacted_value`, `value_hash` | what the approver sees, and the hash of the text that will be typed — **the text itself is never stored** (D1.3, D1.10) |
| `screenshot_sha256` | correlation hash only |
| `payload`, `proposal_hash` | the frozen content and `sha256:` over its RFC 8785 canonical form (`ActionProposal::hashPayload()`, the brief's `content_hash` rule) |
| `nonce`, `idempotency_key`, `frozen_at`, `expires_at` | §11 |
| `executed_at`, `rejected_at`, `rejected_by_user_id`, `rejection_reason` | what happened to it |

Immutability has two halves, because one is not enough:

- **Detection.** `proposal_hash` is recomputed by the executing side —
  `App\Browser\ComputerUse\AuthorizedUiAction` and
  `App\Integrations\Mail\Dto\ApprovedOutgoingEmail` both refuse on mismatch — so an approval can
  never be replayed against different content. `ActionProposal::hashMatchesPayload()` is the check.
- **Prevention.** `App\Models\Approvals\ActionProposal` refuses to persist a change to any column
  outside `MUTABLE_AFTER_FREEZE` (`status` and the four timestamps that record what happened *to* the
  proposal) once `frozen_at` is set, throwing `App\Approvals\FrozenProposalException`. A unique index
  cannot express a per-row rule, which is why this one lives in the model and has its own test
  (`tests/Feature/Approvals/FrozenProposalTest.php`).

Three keys with three different jobs: **`action_proposals_idempotency_key_unique`** (a retried job
cannot create a second approvable proposal), **`action_proposals_nonce_unique`** (the single-use token
an approval must quote), and `action_proposals_proposal_hash_index` — indexed and *not* unique,
because two proposals of identical content are legitimate and differ by nonce. Plus
`action_proposals_organization_status_index`, `action_proposals_organization_kind_status_index`,
`action_proposals_session_frozen_at_index`, `action_proposals_trace_id_index`.

#### `action_approvals` — a replay that cannot be recorded

`action_proposal_id` (FK), `nonce`, `proposal_hash` (copied at approval), `approver_user_id` (FK),
`approved_at`, `expires_at`, the §11 re-auth evidence (`reauth_at`, `auth_device_id`, `ip_address`,
`user_agent` — the last three hidden from serialisation) and `consumed_at`, stamped when the nonce is
spent so an unused expired approval and a used one stay distinguishable.

Two unique indexes, and the pair is the point:

1. **`action_approvals_proposal_unique (action_proposal_id)`** — a proposal can be approved exactly
   once. A second approval from a double-click, a retried request or a stolen screen cannot be
   inserted, even with a fresh nonce.
2. **`action_approvals_nonce_unique (nonce)`** — the proposal's single-use token can be spent exactly
   once across all proposals. An approval replayed with a captured nonce cannot be inserted either,
   even if the attacker also supplies a fresh proposal id.

Together they make a replayed approval **unrecordable** rather than merely detectable, which is the
same argument ADR-009 D1.2 makes for the brief's single-send index. `ActionApproval::authorises()`
adds the fail-closed run-time half: unexpired, unspent, and the hash the approver saw still matching
the proposal's frozen payload. Plus `action_approvals_organization_approved_at_index` and
`action_approvals_approver_approved_at_index`.

| Column | Notes |

### The governance, retention and operations tables (S2-03, #86)

The rest of §3.1 plus the tables the §3.1 list does not carry: `push_subscriptions` from ADR-006
through **ADR-002 D9.5**, and the MCP registry trio's extra columns from **ADR-005 D4.4/D4.6**. They
land empty, on the §1 conventions, so E3-1's eight mail adapters and E3-5's MCP review write into a
schema that already exists — ROADMAP's Sprint 2 gate is explicit that churn after Sprint 3 starts is
expensive across eight adapters. Three rules run through all of it:

1. **A connection row holds a Keychain *reference*, never a credential** (ADR-003 D1):
   `secret_service`, `secret_account`, `secret_version` and nothing else. The contract test asserts
   the absence of any column whose name looks like `token`, `password`, `api_key`, `client_secret`,
   `refresh`, `verifier`, `credential` or `private_key` on `email_connections`, `external_accounts`
   and `mcp_servers`.
2. **No `encrypted:` cast is added here.** S2-04 (#87) owns encryption at rest. These tables
   classify their rows instead — `BusinessObjectColumns::lineage()` now takes the column default, so
   `email_connections` and `external_accounts` default to `personal` and `push_subscriptions` to
   `confidential` — and leave the values plaintext rather than half-applying two items' work.
3. **At most one live row, enforced by an index**, wherever "exactly one active X" is a safety
   property: the `active_marker` generated column plus a unique index, the same portable device
   `brief_deliveries` uses for "exactly one `sent`" (both engines treat NULLs in a unique index as
   distinct). It guards the active privacy policy and the live MCP grant per tool.

`retention_policy` is no longer a dangling name: `app/Security/Retention/` resolves it or throws,
and [retention.md](retention.md) is the rule set. The contract test asserts the schema-wide
property — every table carrying a `retention_policy` column is governed by a rule that resolves
(S2-02's nine AI, approval and memory tables included), and every rule's clock column exists on the
tables it names. `expires_at` is deliberately not one of the five clocks: on
`action_proposals`/`action_approvals`, `browser_sessions`, `ai_providers` and `memories` it is a
business deadline, and an approval that lapsed an hour ago is exactly the row that proves who
consented to what.

### Encryption at rest (S2-04, #87)

Blueprint §3.1 requires sensitive attributes encrypted at rest, and ADR-003 **D1** permits Laravel
`encrypted:` casts for sensitive attributes that are **not** credentials. S2-04 is the only item
permitted to add one; `tests/Security/EncryptedAttributeInventoryTest.php` fails on an `encrypted:`
cast added anywhere else.

The list lives in **`App\Security\Secrets\EncryptedAttributeInventory`**, and the models do not
declare their own casts: `App\Models\Concerns\EncryptsSensitiveAttributes` reads that registry, so the
casts and ADR-003 D8's re-encryption job (`App\Security\Secrets\AppKeyRotation`) are the *same* list
and the job cannot fall behind a cast by omission. The migration is
`2026_10_13_000013_encrypt_sensitive_attributes_at_rest`.

**If `core.app-key` is lost, these columns are unreadable and no support path recovers them.** That is
what made **A25** a hard gate on this item: a keep-data uninstall keeps `core.app-key` and only it, so
the key survives exactly the uninstall that keeps the data, and a delete-everything uninstall takes
both ([uninstall.md](../operations/uninstall.md) §3, §5, §7; ADR-003 D8).
`tests/Feature/Install/ReinstallPreservesDataTest.php` boots twice over one data directory and reads
the encrypted rows back.

#### Uniqueness: `contact_emails.address_hash`

Laravel's encrypter is randomised — `Encrypter::encrypt()` draws a fresh IV, so the same plaintext
yields different ciphertext every time. A unique index over an encrypted column therefore constrains
nothing and an equality lookup never hits. One inventoried column was unique, so its constraint moved:

| Column | Notes |
|---|---|
| `address_hash` | `char(64)`, **keyed** HMAC-SHA256 of the trimmed, lower-cased `address` under a key derived from `core.app-key` (`App\Security\Secrets\BlindIndex`). Carries **`contact_emails_organization_address_unique (organization_id, address_hash)`** — the index keeps the name S2-01 froze and changes its columns |

Same shape as `passkey_credentials.credential_id_hash` (#117): the value lives in a wide, unindexed
column and a fixed-width digest carries the key. `ContactEmail::hashFor()` is the single definition, a
`saving` hook recomputes it from `address` on every write, and `ContactEmail::forAddress()` is the only
way a caller looks one up — §5.6's "the sender address is the primary address of contact X" resolves
through that scope. It is **keyed** where the passkey hash is not, because a credential id is not a
secret while an email address is: the set of plausible addresses is small enough to enumerate, so an
unkeyed digest would be reversible by dictionary and would hand back the value the ciphertext beside it
exists to protect. Rotation therefore rewrites the hash column as well as the ciphertext, and a lookup
asks for the hash under every key in the envelope so an interrupted rotation leaves addresses findable
rather than invisible.

#### Width, the `json` type, and why the `local` profile is untouched

A Laravel payload is base64 of a JSON envelope around the padded ciphertext — roughly **2.4×** the
input — and MySQL runs `STRICT_TRANS_TABLES` here, so an overflow is a hard error and not a silent
truncation (#117 measured exactly that for `credential_id`). Worse, an `encrypted:array` cast writes a
base64 *string*, which MySQL's `json` type rejects outright. So on the `server` profile every
inventoried column becomes **`mediumtext`**, which also moves the `varchar(320)`/`varchar(255)` values
off-page and takes pressure off MySQL's 65 535-byte row-definition limit rather than adding to it.

**None of that touches SQLite.** Its grammar emits no `VARCHAR` length and enforces none, and `json()`
already compiles to `text`, so every one of these columns is already unbounded on `local`; the widening
is skipped there, and the one step that would cost something — Laravel's SQLite grammar implements
`->change()` by rebuilding the table — never runs on the profile the owner uses. On `local` the
migration's only writes are the row rewrites themselves.

#### Bringing existing rows forward

Local installs already hold plaintext rows and `migrate` never re-runs an applied migration, so the
migration rewrites them: `App\Security\Secrets\SensitiveAttributeRewriter` walks the inventory with
`chunkById` (never `chunk` — both loops write to the column they page over, and `chunk()`'s raw-offset
paging skips rows at exactly one past the chunk size, *silently*, which is the bug #117's backfill
shipped with), skips any value that is already a payload, and treats each value as an opaque string so
the plaintext comes back byte-identical rather than through a JSON round trip.

Order matters and is guarded at every step: `address_hash` is added and backfilled from the plaintext
**before** the index moves; a scaffold index over the new columns goes up **before** the old one comes
down, because InnoDB reused `(organization_id, address)` as `contact_emails_organization_fk`'s index and
refuses to drop it otherwise (`SQLSTATE[HY000] 1553`, seen on a clean MySQL 8.4 database and invisible to
every SQLite-only check); `address` is widened **after** the index is gone, because a `TEXT` column
cannot carry an unprefixed key; and the rows are encrypted **last**, because encrypting first would
overflow a column that has not been widened yet. On a fresh install the schema steps run and every row
rewrite is an empty `SELECT`. `tests/Feature/Secrets/SensitiveAttributeRollForwardTest.php` builds a
throwaway database on the pre-S2-04 shape, gives it one row in every inventoried table, runs the one
migration over it, and asserts no row was lost, every value decrypts to its exact bytes, the search
columns were untouched, the index moved and still constrains, and a replay changes nothing.

#### Rotation, and failing closed

`core.app-key` holds `{current, previous[]}` and the Supervisor hands both to
`SecretsServiceProvider`, which sets `app.key` and `app.previous_keys` before the encrypter resolves
(ADR-003 D3.3). So the instant a new key is written every existing row still reads, because Laravel
falls back through `previous_keys` (Evidence E35) — which is what makes
`App\Security\Secrets\AppKeyRotation` safe to be *queued*. It re-encrypts every inventoried value under
the current key, rewrites `address_hash`, and records counts and column names in `audit_events` —
never a value. A value no key can read is counted and reported, never overwritten: that row's contents
are already gone, and writing a re-encrypted nothing over it would destroy the only evidence that a key
was lost rather than rotated.

A read that cannot decrypt raises **`App\Security\Secrets\UnreadableEncryptedAttributeException`**,
naming the model, the attribute, `core.app-key` and the uninstall documentation — never the value or
the key. Nothing returns the ciphertext, an empty string, or a "maybe it is still plaintext" fallback.
Laravel's own `DecryptException` ("The MAC is invalid.") is already fail-closed; what this adds is a
message the person reading the log can act on.

## 3. Round trip with the brief and CRM fixtures

`App\Briefs\BriefDocumentMapper::import()` is the freeze transaction of brief schema §5 (brief row,
items, deliveries, one commit; the document's `content_hash` must match or the import is refused).
`export()` rebuilds the document in schema key order. `tests/Feature/Briefs/BriefRoundTripTest.php`
imports every `packaging/fixtures/briefs/*.json` and proves the export is byte-identical on the JCS
canonical form; `tests/Unit/Support/JcsTest.php` proves the PHP JCS port (`App\Support\Json\Jcs`)
reproduces every frozen `content_hash`.

`App\CRM\Import\CrmPackMapper` does the same for the CRM pack, and
`tests/Feature/CRM/CrmFixtureRoundTripTest.php` proves every record in
`packaging/fixtures/crm/*.json` comes back with identical field values — including the two customers
that share an email domain and the invoice whose domain match a user corrected. Two normalizations
are deliberate and asserted rather than hidden: timestamps round-trip as **instants rendered in
UTC**, because the CRM pack (unlike the brief schema) carries no `utc_offset` and §3.1 stores UTC;
and the pack's pure id arrays (`customer_ids`, `contact_ids`, `assignee_user_ids`) are `uniqueItems`
sets in `crm.schema.json`, so they come back ordered by id, while the ordered nested lists
(`emails`, `github_links`) keep their exact order through a `position` column.

## 4. Processes and heartbeats (ADR-002 D1, §12.2)

Three `launchd`-supervised processes (S1-07) run beside each other on the `local` profile:

| Process | Command | Health check that notices when it stops |
|---|---|---|
| HTTP | the bundled server (ADR-001) | `http` (and `/health/live`) |
| Scheduler | `php artisan schedule:work` | `scheduler_selftest` — `health:selftest` runs every minute, threshold 180 s |
| Worker | `php artisan queue:work database --queue=briefs,email-sync,default,ai --sleep=3 --tries=3` | `queue_worker` — heartbeat from the worker loop, threshold 90 s |

Heartbeats are cache entries under `health:heartbeat:<name>` (`App\Support\Health\Heartbeats`); the
menu bar's IPC heartbeat (S1-08) writes `menubar`. Thresholds live in `config/health.php`.

## 5. Backend profiles

`LEA_BACKEND_PROFILE` (`config/lea.php`, default `local`) selects ADR-002 D1's profile. The
`server` profile (MySQL 8.4 + Redis) is exercised by the `backend-contract` Pest group in
`tests/Integration/BackendContract/`, which skips itself unless `DB_CONNECTION=mysql` is actually
configured. Id-like columns on MySQL need `utf8mb4_bin` collation (D10); that is applied by the
MySQL grammar class when the profile is wired, not by the migrations.

To run the group against MySQL locally, point the connection at a database that exists only for
this purpose and migrate it first — never at a database with data in it, and never with
`migrate:fresh`, `migrate:refresh` or `db:wipe`:

```bash
mysql -h127.0.0.1 -uroot -e "CREATE DATABASE IF NOT EXISTS lxai_contract_test CHARACTER SET utf8mb4"
export LEA_BACKEND_PROFILE=server DB_CONNECTION=mysql DB_HOST=127.0.0.1 DB_PORT=3306 \
       DB_DATABASE=lxai_contract_test DB_USERNAME=root DB_PASSWORD=
php artisan migrate --force
vendor/bin/pest tests/Integration/BackendContract tests/Feature/CRM
```

The shell variables win over `phpunit.xml`'s `<env>` defaults, which are not forced. The whole suite
is **not** expected to pass with those variables set: tests that assert the `local` profile, the
SQLite WAL pragma check and the E2E installer (which builds its own SQLite data directory) fail by
construction on a MySQL connection. ADR-002 D10's matrix is about the `backend-contract` groups.
